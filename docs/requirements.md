# Webhook Platform Requirements

## 1. Product Goal

Build a standalone Webhook Delivery Platform that receives domain events from producer applications and reliably delivers them to subscribed external HTTP endpoints.

The first real producer is the existing AI Study Assistant.

The platform separates event-producing applications from webhook delivery concerns such as:

- endpoint management
- subscription management
- asynchronous delivery
- retries
- delivery history
- security
- debugging
- observability

---

## 2. Problem Statement

Applications often need to notify external systems after domain events occur.

Without a shared webhook platform, each application would need to independently implement:

- endpoint storage
- event subscription rules
- HTTP delivery
- retry logic
- request signing
- failure handling
- delivery logs
- monitoring

The Webhook Platform centralizes these responsibilities.

---

## 3. Actors

### 3.1 Producer

An application that publishes events to the Webhook Platform.

Initial producer:

- AI Study Assistant

Examples of producer events:

- `ai.solution.completed`
- `ai.grade.completed`
- `ai.answer.reported`

### 3.2 Developer

A user of the Webhook Dashboard who can:

- create applications
- create API keys
- configure endpoints
- subscribe endpoints to events
- inspect events
- inspect deliveries
- inspect attempts
- manually retry failed deliveries

### 3.3 Consumer

An external HTTP service that receives webhook requests.

Example consumers:

- analytics service
- notification service
- quality monitoring service
- mock endpoint for testing

## 4. Functional Requirements

### FR-01 Application Management

The platform must allow a developer to:

- create an application
- view applications
- view application details
- enable or disable an application

### FR-02 API Key Management

The platform must allow a developer to:

- create an API key for an application
- view key metadata
- revoke an API key

The full API key must only be shown at creation time.

### FR-03 Endpoint Management

The platform must allow a developer to:

- create a webhook endpoint
- edit endpoint name and URL
- enable or disable an endpoint
- view endpoint health information
- rotate its signing secret

### FR-04 Event Subscription

The platform must allow an endpoint to subscribe to one or more event types.

An endpoint must not contain duplicate subscriptions for the same event type.

### FR-05 Event Ingestion

A producer must be able to publish an event through the Producer API.

The platform must:

1. authenticate the producer
2. validate the event
3. protect against duplicate source events
4. persist the event
5. find matching subscriptions
6. create deliveries
7. return without waiting for external endpoint delivery

### FR-06 Delivery Creation

For every subscribed endpoint matching an event type, the platform must create one delivery.

An event may therefore produce:

- zero deliveries
- one delivery
- multiple deliveries

### FR-07 Asynchronous Delivery

Webhook HTTP requests must be sent asynchronously.

The producer request must not wait for external consumers.

### FR-08 Delivery Attempts

Every physical outbound HTTP request must be represented as a delivery attempt.

The platform must persist useful debugging metadata for attempts.

### FR-09 Automatic Retry

Transient delivery failures must be retried according to the configured retry policy.

### FR-10 Terminal Failure

When the maximum number of delivery attempts is exhausted, the delivery must become `FAILED`.

### FR-11 Manual Retry

A developer must be able to request a retry for an eligible failed delivery.

The implementation must preserve attempt history.

### FR-12 HMAC Signing

Webhook requests must be signed so that consumers can verify authenticity.

### FR-13 Delivery Inspection

The dashboard must allow developers to inspect:

- event
- endpoint
- delivery status
- attempt count
- attempt timeline
- HTTP response status
- latency
- safe request metadata
- safe response metadata

### FR-14 Event Inspection

The dashboard must allow developers to inspect:

- event ID
- source application
- event type
- received timestamp
- event payload
- deliveries generated by the event

## 5. Initial Event Catalog

### `ai.solution.completed`

Emitted when the AI Study Assistant successfully completes generation of a solution.

Recommended payload:

```json
{
  "solutionId": "sol_123",
  "subject": "mathematics",
  "status": "COMPLETED"
}
```

### `ai.grade.completed`

Emitted when AI grading completes.

Recommended payload:

```json
{
  "submissionId": "sub_123",
  "status": "COMPLETED"
}
```

Avoid exposing unnecessary answer or student content in the webhook event.

### `ai.answer.reported`

Emitted when an AI-generated answer is reported for quality review.

Recommended payload:

```json
{
  "solutionId": "sol_123",
  "reason": "incorrect_solution"
}
```

## 6. Non-Functional Requirements

### NFR-01 Delivery Guarantee

Version 1 provides **at-least-once delivery**.

Duplicate webhook delivery is possible.

### NFR-02 Producer Isolation

A slow or unavailable consumer must not block event ingestion from a producer.

### NFR-03 Persistence

Events, deliveries, and delivery attempts must survive application restart.

### NFR-04 Concurrency Safety

Multiple workers must not normally claim and process the same pending delivery concurrently.

### NFR-05 Observability

Every event, delivery, and attempt must have stable identifiers.

### NFR-06 Debuggability

A developer must be able to understand why a delivery succeeded, retried, or failed without relying only on server logs.

### NFR-07 Security

- raw API keys must not be stored
- signing secrets must be protected
- webhook requests must be signed
- secrets must not appear in logs

### NFR-08 Performance

The event ingestion endpoint should perform only the work necessary to:

- validate
- persist
- create delivery work

External HTTP delivery occurs after the ingestion request returns.

### NFR-09 Maintainability

Version 1 should remain a modular monolith.

Complex infrastructure must not be added without demonstrated need.

## 7. Delivery Statuses

Supported delivery states:

```text
PENDING
PROCESSING
RETRYING
DELIVERED
FAILED
```

General state flow:

```text
PENDING
   |
   v
PROCESSING
   |
   +--> DELIVERED
   |
   +--> RETRYING
           |
           v
       PROCESSING
           |
           +--> DELIVERED
           |
           +--> FAILED
```

Manual retry behavior is defined in `retry-policy.md`.

## 8. MVP Scope

Version 1 includes:

- applications
- API keys
- endpoints
- subscriptions
- event ingestion
- event idempotency
- delivery creation
- PostgreSQL-backed delivery worker
- delivery attempts
- retry
- HMAC signing
- dashboard
- AI Study Assistant integration
- failure testing

---

## 9. Out of Scope for Version 1

Do not implement unless requirements change:

- Kafka
- Redis
- Kubernetes
- microservices
- billing
- organizations
- team permissions
- additional OAuth providers beyond Google
- multi-region delivery
- advanced routing rules
- webhook transformations
- guaranteed ordering across all events
- exactly-once delivery
